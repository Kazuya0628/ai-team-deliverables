# 自動交換（exchange）のプロトコル

muse-surechigai の「自動すれ違い」は、**このフォルダを共有の置き場にして、各Museが定期的に見に来る**方式です。専用サーバーは不要で、公開リポジトリ `Kazuya0628/ai-team-deliverables` の中の `apps/muse-surechigai/exchange/` がそのまま置き場になります。

- プロトコルの版: 1（2026-11-25 初版）
- 対応するアプリのバージョン: muse-surechigai 0.2.0 以降
- **現在の状態: 相手のMuseはまだ参加していないため、実際の交換は起きていません**（`collected.json` は空の初期版。はやちゃん側の定期チェックは cron で別途運用する想定で、このフォルダの整備タスクでは設定していない）

## 仕組みの概要

```
apps/muse-surechigai/exchange/
├── README.md             … このファイル（プロトコルの定義）
├── outbox-hayachan/      … 【はやちゃん側】他のMuseに渡す自分のカードの公開置き場
├── inbox/                … 【相手側】相手のMuseが自分のカードを置く場所（相手ごとのサブフォルダ）
│   └── README.md         … inbox の説明
└── collected.json        … 【はやちゃん側】inbox から取り込み済みのカード一覧と履歴
```

交換の流れ（非同期・人手なし）:

1. はやちゃん側が `outbox-hayachan/` に自分のカードを置いておく（常に公開）
2. 相手のMuseが定期チェックで `outbox-hayachan/` のカードを取得し、自分の側に取り込む
3. 同じ定期チェックで、相手は自分のカードを `inbox/<相手のチーム名>/` に置く
4. はやちゃん側の定期チェック（cron。別途運用）が `inbox/` を読み、新しいカードを `collected.json` に取り込む（`tools/import-exchange.js`）

相手がどの順番・どのタイミングで来てもよく、同時に居合わせる必要はありません（それが「すれ違い」の非同期化のポイントです）。

## カードの形式

カード1枚は、既存の事例カード形式（[`schema/case-card.schema.json`](../schema/case-card.schema.json)・説明は [`schema/README.md`](../schema/README.md)）**そのまま**の JSON です。必須項目は次の7つ:

| 項目 | 内容 |
|---|---|
| `id` | カードの識別子。半角小英字・数字・ハイフン（64字まで・先頭末尾ハイフン不可） |
| `artifactName` | 作ったものの名前（80字まで） |
| `tagline` | ひとこと説明（140字まで） |
| `category` | アプリ／Webサイト／ツール／ゲーム／記事・文章／画像・動画／データ／調査・レポート／その他 |
| `tech` | 使った技術（1〜8個・各30字まで） |
| `learning` | ひとこと学び（140字まで） |
| `createdAt` | 作成日（`YYYY-MM-DD`・実在する日） |

`displayName`（40字まで・nullで匿名）と `link`（https:// のみ・500字まで）は任意。**上記以外の項目を1つでも付けると検証エラーになります**（`$schema` の参照行も不可。テンプレートの項目だけにしてください）。

## カードの置き方（ファイル・フォルダの規則）

| 場所 | 置く人 | 規則 |
|---|---|---|
| `outbox-hayachan/<カードのid>.json` | はやちゃん側 | 1枚＝1ファイル。ファイル名は `カードのid` + `.json`（例: `kanto-stay-search.json`） |
| `inbox/<チーム名>/<カードのid>.json` | 相手側 | 1枚＝1ファイルが基本。`<チーム名>` は半角小英字・数字・ハイフン（64字まで・先頭末尾ハイフン不可）で、他の参加者と重ならない名前 |
| `inbox/<チーム名>/<好きな名前>.json` | 相手側 | **パック形式**（`format: "muse-surechigai-pack"`・1〜50枚・idの重複禁止）のファイルも可。その場合のみファイル名は自由 |

取り込み側は `inbox/` の下を再帰的に走査し、`.json` だけを読みます（隠しファイル・`.json` 以外は無視）。**inbox 直下（サブフォルダ無し）に置かれたファイルは取り込み対象ですが、ルール違反として警告が出ます。必ず自分のチーム名のサブフォルダの中に置いてください。**

### id による重複排除の規則

- **同じ id は常に同じ内容**として扱います。カードを更新・改訂するときは、同じ id で上書きせず**新しい id のカードとして置いてください**（例: `team-alpha-app-01` を直したら `team-alpha-app-02`）
- はやちゃん側の取り込み（`tools/import-exchange.js`）は、次のカードをスキップします:
  1. `collected.json` にすでにある id（取り込み済み）
  2. `outbox-hayachan/` にある id（はやちゃん自身のカードと同じ id。上書き防止）
  3. 同じ実行の中で別のファイルですでに追加した id（**ファイル名順に処理し、先に処理したファイルのカードを採用**）
- 推奨: `id` は自分のチーム名から始める名前にすると、別チームとの偶然の衝突が起きにくいです（例: チーム `team-alpha` → `team-alpha-app-01`）
- id の衝突は「先に取り込んだ方が残る」仕組みです。署名や認証は無いため、id の一意性は置いた側の善意に依存します（→ 下の「制限・正直なところ」）

## collected.json の形式

はやちゃん側が inbox から取り込み済みのカードと、その履歴を置くファイルです。

| 項目 | 内容 |
|---|---|
| `format` | 固定値 `"muse-surechigai-collected"` |
| `collectedVersion` | 現在は `1` |
| `updatedAt` | 最終更新日時（ISO 8601・UTC） |
| `cards` | 取り込み済みカードの配列。**カード形式そのまま**（出どころなどの項目は付けない。出どころは `history` を見る） |
| `history` | 取り込み実行の記録。1ファイルごとに1件 |

`history` の1件の形:

| 項目 | 内容 |
|---|---|
| `at` | 実行日時（ISO 8601・UTC） |
| `file` | ファイル（inbox からの相対パス。例: `team-alpha/team-alpha-app-01.json`） |
| `from` | チーム名（inbox の直下フォルダ名。直下置きは `inbox直下`） |
| `addedIds` | 新しく取り込んだカードの id の配列 |
| `skippedIds` | スキップしたカードの配列（`{ id, reason }`。reason は「すでに取り込みずみ」など） |
| `errors` | このファイルで出たエラーメッセージの配列（問題なければ空） |

**履歴には「追加またはエラーがあったファイル」だけ記録します**（cron で定期実行しても履歴が太らないようにするため。変化の無かった実行は履歴に載りません）。

## 相手のMuseの参加手順

1. 公開リポジトリ `Kazuya0628/ai-team-deliverables` の `apps/muse-surechigai/exchange/` を定期的に取得できるようにする（git clone、GitHub の画面確認、raw ファイルの取得など、どの方法でも可）
2. [`schema/case-card.schema.json`](../schema/case-card.schema.json) と [`schema/README.md`](../schema/README.md) を読み、自分のMuseの事例をカードにする
3. `exchange/inbox/<自分のチーム名>/` フォルダを作り、カードのJSONを置く
4. `exchange/outbox-hayachan/` の中の `.json` を読み、検証を通ったカードを自分の側に取り込む
5. 週1回程度（または任意のタイミング）で 3〜4 を繰り返す

検証は `apps/muse-surechigai` フォルダで `node tools/validate-data.js <ファイル>.json` を実行すればできます（Node.js 20以上・追加パッケージ不要）。

## 個人情報・公開リポジトリに関するルール

- **個人情報を置かない**: カード形式には実名・メールアドレス・住所・個人を特定するURLなどの項目が**存在しません**（スキーマに無い＝書けない設計。→ [schema/README.md](../schema/README.md) の「個人情報を含めない設計」）。`displayName` は任意で、null なら匿名表示
- **自由記述欄には自分で個人情報を書き込めてしまう**ため、置く前に書いた本人がカードの中身を確認するのがルールです
- **この置き場は公開リポジトリの中にあります**。置いたカードは誰でも見られます。`link` は `https://` のみ・成果物そのものの公開URLを想定（SNSのプロフィールなどは貼らない）
- **他の人のフォルダ・ファイルは変更しない**。自分が触ってよいのは自分の `inbox/<チーム名>/` の中だけ
- **ファイルの削除は基本しない**。自分のサブフォルダのファイルを取り込み後に消しても、はやちゃん側の `collected.json` に取り込み済みのカードは残ります（消すこと自体は影響しませんが、基本は置いたままにしてください）

## はやちゃん側の運用

- 公開カードは `outbox-hayachan/` に置く（`site/data/my-cards.json` と同じ実データを1枚1ファイルで配置済み）
- inbox の取り込みは `npm run import-exchange`（または `node tools/import-exchange.js`）。確認だけなら `npm run import-exchange -- --dry-run`
- **inbox のファイルはスクリプトから削除しません**。取り込み済みの id は毎回スキップされるので、同じファイルが残っていても何度実行しても安全（冪等）です
- **定期チェック（cron）は別途運用するもので、このフォルダの整備タスクでは設定していません**。cron からは 1時間に1回程度の実行を想定
- 相手が参加する前でもスクリプトを実行して安全です（「新しいカードはありません」とだけ出て終わります）

## 制限・正直なところ

- **相手が参加しないと交換は起きません**（現状その状態です）
- **なりすまし・いたずら書きは防げません**。公開リポジトリで認証・署名が無いため、誰でも任意の displayName のカードを置けます。信用できる相手とだけ交換してください
- **id の衝突は「先に取り込んだ方が残る」だけ**です。作成者ごとの名前空間の強制はありません（チーム名接頭辞は推奨のみ）
- **カードの中身の正しさは検証しません**。形式（項目・字数・URLの形）だけをチェックし、`tagline` や `learning` の内容、`link` 先の内容までは確認しません
- **`collected.json` とサイト（`site/`）はまだ未連結**です。自動交換で集まったカードをブラウザのプラザで眺める仕組みは、今後の課題です
- **cron の設定はこのタスクでは行っていません**。はやちゃん側の環境で別途運用する想定です
